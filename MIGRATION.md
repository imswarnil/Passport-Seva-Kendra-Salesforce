# MIGRATION.md — From 17 Objects to 8

> **⚠️ This document describes destructive changes to `psk-dev`. Nothing in it has been executed.**
> The target state is [DATA_MODEL.md](DATA_MODEL.md). Read [§2 Sign-off](#2-sign-off-required) before running anything.

---

## 1. What is being destroyed

| Category | Count | Recoverable? |
|---|---|---|
| Custom objects (PSK) | 10 | **No.** Deleting a custom object deletes every record in it, permanently, along with its fields, validation rules, layouts and record types. |
| Custom objects (inherited Wave) | 2 | **No.** Also breaks the Service Analytics dashboards. |
| Records in those objects | ~500 | **No.** They sit in the Recycle Bin briefly, then go. |
| Apex classes | ~14 | Yes — they are in Git. |
| LWC bundles | ~4 | Yes — in Git. |
| FlexiPages, layouts, tabs, quick actions | ~30 | Yes — in Git. |
| Custom apps | 4 | Yes — in Git. |

**The metadata is recoverable from Git. The data is not.** That asymmetry is the whole risk profile of this migration.

## 2. Sign-off required

Three decisions need an explicit yes before anything runs. Each is irreversible.

### ☐ 2.1 — Delete ~500 demo records

The ten PSK objects being removed contain roughly 500 records (94 appointments, 66 slots, 60 family members, 56 print jobs, and so on). They are demo data generated by `PSK_DemoDataGenerator`, not anything a human authored — but "demo data" is a claim worth verifying before acting on it. §3 step 0 exports everything first.

### ☐ 2.2 — Break the Service Analytics dashboards

Deleting `OpportunityHistory__c` and `Reseller_Account_Plan__c` breaks the CRM Analytics dashboards that shipped with the org, permanently. PSK reads none of it, and CRM Analytics is out of scope per [SOLUTION.md §7](SOLUTION.md) — but if you ever want to learn Phase 11b against those templates, this closes that door.

**The upside:** it is also what fixes the six failing inherited tests (`DataManager_QuotaTest`, `DataManager_CleanUpTest`, `DataManager_OpportunityTest`, `DataManager_controllerTest`, `DataManager_OpportunityRelatedTest`, `DataManager_ActivityTest`), which fail on a hard-coded date and have nothing to do with PSK.

**Alternative if you'd rather not:** keep both objects and their `DataManager_*` classes. Cost is a permanently red test run and a slower retrieve. This is a genuine trade — a red suite trains you to ignore red suites.

### ☐ 2.3 — Override the standing guardrail

[PSK.md §10](PSK.md) says *"Do not delete metadata or data without asking"* and *"Some of it is load-bearing for the Wave dashboards."* This migration is that ask. Approving it supersedes the guardrail for this operation only.

## 3. The order of operations

Salesforce refuses to delete an object while anything still references it. The teardown is therefore strictly bottom-up, and each step must succeed before the next.

### Step 0 — Back up (not optional)

```bash
# Full metadata snapshot
git checkout -b pre-migration-snapshot && git push -u origin pre-migration-snapshot

# Export every record from every object being deleted
mkdir -p backup/pre-migration
for o in Payment__c Print_Job__c Objection__c Risk_Flag__c Family_Member__c \
         Notification_Log__c Renewal__c Visa_Application__c Appointment__c Slot__c; do
  sf data query --query "SELECT FIELDS(ALL) FROM $o LIMIT 2000" \
     --result-format csv > "backup/pre-migration/$o.csv"
done

# Request an org-level data export as a second safety net
sf org open --path lightning/setup/DataManagementExport/home
```

**Do not proceed until `backup/pre-migration/` contains a non-empty CSV for every object.**

### Step 1 — Apex first

Apex referencing a deleted object will not compile, and a non-compiling class blocks the object's deletion. These go first.

**Delete outright** (their whole reason for existing is a cut object):

`AppointmentTriggerHandler` · `AppointmentTriggerHandlerTest` · `AppointmentTrigger` · `PaymentTriggerHandler` · `PaymentTriggerHandlerTest` · `PaymentTrigger` · `PSK_SlotBookingController` · `PSK_SlotBookingControllerTest` · `PSK_OfficeCapacityController` · `PSK_OfficeCapacityControllerTest` · all `DataManager_*` classes and their tests

**Edit to remove references** (they survive, minus the cut objects):

| Class | Remove |
|---|---|
| `PSK_Constants` | `Payment__c`, `Print_Job__c` constants |
| `PSK_ApplicationService` | `Print_Job__c` minting — folds into `Dispatch__c` |
| `PassportApplicationTriggerHandler` | `Print_Job__c` branch |
| `PSK_ApplicationSidebarController` | `Payment__c`, `Risk_Flag__c` queries |
| `PSK_ApplicationTimelineController` | `Payment__c`, `Print_Job__c`, `Objection__c`, `Notification_Log__c`, `Appointment__c` |
| `PSK_Citizen360Controller` | `Family_Member__c`, `Risk_Flag__c` |
| `PSK_HomeController` | `Risk_Flag__c`, `Appointment__c` counts |
| `PSK_PassportIssuanceController` | `Print_Job__c` |
| `PSK_DemoDataGenerator` | rewritten wholesale against the new scenarios ([DEMO_DATA.md](DEMO_DATA.md)) |
| `PSK_TestDataFactory` | replaced by `PSK_TestFactory` ([TESTING.md §3](TESTING.md)) |

Every corresponding `*Test` class needs the same treatment.

### Step 2 — LWC

`pskMyWorkQueue` (references six cut objects), `pskFulfilmentBoard` (`Print_Job__c`), `pskCitizen360` (`Family_Member__c`). Edit rather than delete — each has a job in the new model.

### Step 3 — UI metadata

FlexiPages `Print_Job_Record_Page`, `Family_Member_Record_Page`, `Slot_Record_Page` and the other cut-object record pages. All layouts for cut objects, plus the four `Passport Application Layout*` variants that carry related lists for cut objects. Quick action `Citizen__c.New_Family_Member`. Tabs for every cut object. Object translations under `objectTranslations/Appointment__c-en_US/`.

### Step 4 — Apps

Delete `PSK_Operations_Console`, `Passport_Validator`, `PSK_Police_Verification_Console`, `Trailhead_Data_Manager`. Strip cut-object tabs from `Application_Management_Console` before it is renamed and re-scoped as App 1.

### Step 5 — Permission sets and profiles

**Edit, do not delete.** Remove the `objectPermissions`, `fieldPermissions`, `tabSettings` and `recordTypeVisibilities` blocks for cut objects from all nine permission sets. Delete `PSK_Visa_Officer` outright (its only object is going).

> **Profiles are the trap in this migration.** Dozens of standard profiles (`Admin`, `Analytics Cloud Integration User`, `Chatter Free User`, and ~30 more) carry references to these objects because a full-org retrieve pulled them all down. Deleting an object *usually* cleans profile references server-side, but a subsequent deploy of a stale local profile will fail on the now-missing object. **Delete the local profile files for every profile except `Admin` before deploying** — they are retrieve noise, not build artefacts, and nothing in PSK depends on them.

### Step 6 — Sharing rules, queues, groups

Remove sharing rules on cut objects (`Open_High_Severity_To_Managers` on `Risk_Flag__c`, `Expiring_To_Officers` on `Passport__c`). Delete queues `Objections`, `Risk_Review`, `Granting`. Delete groups `PSK_Verification_Team`, `PSK_Fulfilment_Team`, `PSK_Visa_Team`. Delete roles per [ACCESS_MATRIX.md §3](ACCESS_MATRIX.md) — **roles last, and only after every user is reassigned**, since deleting a role with users assigned fails.

### Step 7 — The objects themselves

Only now. `manifest/destructiveChanges.xml` is staged and ready.

```bash
# Validate first — ALWAYS. This runs the whole delete without committing it.
sf project deploy start \
  --manifest manifest/destructive-package.xml \
  --post-destructive-changes manifest/destructiveChanges.xml \
  --dry-run --verbose

# Only if the dry run is clean:
sf project deploy start \
  --manifest manifest/destructive-package.xml \
  --post-destructive-changes manifest/destructiveChanges.xml
```

The dry run is the single most important command in this document. It surfaces every remaining reference without destroying anything, and a clean dry run means steps 1–6 were complete.

### Step 8 — Verify

```bash
sf apex run test --test-level RunLocalTests --result-format human --code-coverage
sf project retrieve start --manifest manifest/package.xml   # confirm the org matches
```

Expect: **zero failing tests** — including the six inherited ones, which are now gone rather than fixed.

## 4. Rollback

| Step | Reversible? | How |
|---|---|---|
| 0–6 (metadata) | **Yes** | `git checkout pre-migration-snapshot` and redeploy |
| 7 (objects) | **No** | Objects and their records are gone. The CSVs in `backup/pre-migration/` are the only copy, and reloading them requires recreating the objects first |

**Once step 7 runs, forward is the only direction.** Everything before it exists so that step 7 succeeds on the first attempt.

## 6. Manual steps metadata cannot express

Two things must be done by hand in Setup after the deploys, every time:

1. **Per-record-type Lightning page activation.** Org-default and app-default assignments deploy; per-record-type activation does not reliably survive `FlexiPage` metadata. After any deploy touching record pages: Lightning App Builder → Activation → assign the application record page against all five record types.
2. **Case channel setup.** Email-to-Case, auto-response rules and Omni-Channel involve Setup toggles that are not fully representable in source. App 2 needs these turned on before its assignment and escalation rules do anything.

Neither is a defect. Knowing which parts of a Salesforce org *cannot* live in source control is part of the DevOps lesson.
