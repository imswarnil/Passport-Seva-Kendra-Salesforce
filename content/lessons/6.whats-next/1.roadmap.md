Every lesson so far describes something that is actually built and deployed. This one is different: it's the status report, written the way a real handoff document should be — with the gaps named instead of hidden, and a reason attached to each one.

## Built and deployed

| Layer | What |
|---|---|
| Data model | All 17 objects (see the [object catalogue](/data-model/the-object-catalogue)), ~250+ custom fields, 9 record types across 2 objects, `Fee_Matrix__mdt` (10 records), `SLA_Config__mdt` (26 records) |
| Vocabulary | 13 global value sets |
| Validation | 62 validation rules across every PSK object (13 on `Passport_Application__c` alone) |
| Security | 11 roles, 6 public groups, 6 queues, 9 criteria-based sharing rules, 9 persona permission sets, 3 permission set groups |
| Apex | 4 triggers + handlers, ~18 service/controller classes, all with test classes; 233 local tests, the large majority green |
| Automation | Auto-assignment to queues on status transition, auto-generated document checklists, the Diplomatic/Official approval process, auto-minted `Passport__c` + `Print_Job__c` + `Dispatch__c` on entering their stages |
| UI | 4 custom apps, 22 tabs, Lightning Record Pages for every object (FlexiPages exclusively, no classic Layouts), 14 LWC bundles, a Path on the Fresh record type |

## In flight — known gaps, not surprises

- **`Family_Member__c` has no dedicated FlexiPage** — reachable only via a quick action on `Citizen__c`.
- **The Path only renders on the `Fresh` record type** — the other five record types (including Diplomatic_Official, the one with the extra approval stage) show no stage bar.
- **PII field-level security drift** — a handful of permission sets still have some PII fields editable where the design intent says read-only (flagged in [the security lesson](/security/security-model)). Worth a permission-set audit as a practice exercise.
- **`Visa_Application__c` has no Apex automation yet** — the object, its validation rules, its tab and its permission set are built and deployed, deliberately scoped as a metadata-only MVP (see [Four Apps](/foundations/four-apps)). No trigger or service class yet — no auto-routing to a queue, no fee lookup, no notifications. A natural next step is adding the same trigger → handler → service layer that `PassportApplicationTrigger` uses.

## Not started, with reasoning

**Experience Cloud citizen site.** The applicant journey is entirely staff-mediated by design (see the assumptions in [The Problem](/foundations/the-problem)) — there is no portal. Enabling Digital Experiences is a one-way Setup toggle, in the same category as Enterprise Territory Management: it provisions a community domain, requires licenses that may not exist on every Developer Edition org, and can't be fully expressed or verified through a metadata deploy alone. Flipping it blind risks leaving an org half-configured in a way that's hard to undo — it needs a human to make the licensing/domain decision first, deliberately, not as a side effect of a deploy script.

**n8n / Twilio / AI integrations.** `Notification_Log__c` exists with a `Provider_Message_Id__c` idempotency key, ready for it and currently empty of real sends. This is the highest-value unbuilt layer, and it's worth its own section below because the roadmap for it is concrete, not vague.

**Hindi / regional translation.** `objectTranslations/` are English-only stubs, despite `Citizen__c.Preferred_Language__c` existing as a field. Lower priority than the gaps above — genuinely just not gotten to yet.

## What NOT to do to this org

A few standing rules, carried over from how this build has been operated, worth knowing before you go fork it and start changing things:

- **Do not enable Enterprise Territory Management** without an explicit decision — it's irreversible and the current sharing design doesn't assume it.
- **Do not write a picklist string literal in Apex.** Use `PSK_Constants`.
- **Do not add a cross-object formula to the applicant declaration fields** on `Passport_Application__c` — that duplication is the design, covered in [Fields & Formulas](/data-model/fields-and-formulas).
- **Do not deploy the whole tree when a scoped deploy will do.** A full `--source-dir force-app` deploy drags in an unrelated Wave Analytics template that came bundled with the Developer Edition org.

## The integration roadmap, concretely: n8n as the outside-the-org layer

Salesforce already does its own *internal* automation — triggers, the approval process, queue routing, validation rules, sharing rules. None of that needs an external tool. What's missing is everything **outside the org boundary**: sending SMS/WhatsApp, receiving payment-gateway and courier webhooks, running AI over documents, firing scheduled outreach with no natural Salesforce-side trigger. n8n (or an equivalent workflow tool) is the natural place for exactly that layer — bolted onto the org, not a replacement for anything Apex or the approval process already own.

Three concrete pieces of that roadmap, in priority order:

::flow{title="First-wave automations, if you pick this up" :steps='["Status-change SMS/WhatsApp — the single most applicant-visible gap; the object model (Notification_Log__c, Mobile_For_Alerts__c, Notification_Consent__c) was built for exactly this", "Payment reminder — a scheduled poll for applications stuck in Payment Pending; stuck-in-payment is a common real-world drop-off point and directly recoverable", "Appointment reminder — day-before and morning-of reminders for a booked Slot__c; a booked slot going unused is expensive, and reminders are cheap"]'}
::

**The connection pattern**, so a future implementer doesn't have to re-derive it: Salesforce → n8n via Platform Events (for near-real-time, per-record fan-out) or scheduled polling of a REST/Apex REST endpoint (for batch-shaped work like an SLA sweep). n8n → Salesforce via the standard REST API, using the `External_Id__c` every PSK object already carries so writes are idempotent upserts rather than query-then-insert.

::warning{title="Auth: JWT Bearer, not username-password"}
The standard headless server-to-server pattern here is a Connected App with OAuth 2.0 JWT Bearer Flow — the integration holds a private key, signs a JWT, exchanges it for an access token with no interactive login and no refresh-token expiry risk. This is the exact same pattern this platform's own read-only [demo org](/demo-org) proxy uses to talk to the org — worth reading that code alongside this section, since it's a live, working example of the auth flow described here.
::

## The habit this whole lesson is modeling

None of the gaps above are hidden, and none of them are dressed up as "coming soon" marketing. They're recorded the way [The Problem](/foundations/the-problem) argued a design decision's cost should be recorded — plainly, with a reason, so the next person (possibly you, forking this org) knows exactly where to pick up.
