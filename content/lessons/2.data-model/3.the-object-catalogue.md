The earlier lessons walk through the *reasoning* behind individual objects one at a time. This lesson is the flat reference: every object that is actually built and deployed in the org, in one table, so you have something to check a claim against instead of trusting a lesson's memory of it.

Two objects were not in the original plan at all and were added because the model needed them: `Citizen__c` (a golden identity record, so the applicant is not modelled as an Account) and `Family_Member__c` (citizen-to-citizen links, which also carry the guardian link a minor application needs).

## The as-submitted snapshot — a deliberate duplication

`Passport_Application__c` carries its own `First_Name__c`, `Last_Name__c`, `Date_of_Birth__c`, `Mobile__c` and full address **even though it also has a `Citizen__c` lookup**. That is on purpose, and it's the subject of the whole [Fields & Formulas](/data-model/fields-and-formulas) lesson: `Citizen__c` answers "who is this person now"; the application answers "what did they declare then." Both are needed, and they are allowed to disagree.

## Where duplication *is* avoided

The rule of thumb from that same lesson: **snapshot a declaration, derive a fact.**

- `Passport__c` re-keys nothing — `Booklet_Pages__c`, `Validity_Years__c`, `ECR_Status__c` and `Passport_Category__c` are formulas over the application; `Holder_Name__c` is assembled by formula from the application's name parts; `Place_of_Issue__c` is `PSK_Office__r.Name`. Only the booklet's own facts — file number, issue/expiry dates, status — are stored.
- `Dispatch__c.Delivery_Address__c` is a formula over `Passport_Application__r`'s address lines, so a courier label can never drift from the application.
- `Family_Member__c` reads `Member_Date_of_Birth__c` and `Member_Mobile__c` through `Related_Citizen__r`; `Display_Name__c` falls back to a typed `Member_Name__c` only when no citizen is linked.
- `Print_Job__c.ARN__c` and `Dispatch__c.ARN__c` are `Passport_Application__r.Name`, not stored strings.

## Naming conventions, if you're reading the metadata directly

- **Objects:** singular label, PascalCase API with underscores, e.g. `Passport_Application__c`.
- **Fields:** descriptive, no abbreviations, e.g. `Police_Verification_Type__c` not `PV_Typ__c`.
- **Picklists:** restricted value sets, reusing a Global Value Set for anything shared across objects (thirteen exist — `Indian_States`, `PSK_Gender`, `PSK_Payment_Status`, and so on).
- **Record types:** business name, no prefix (`Fresh`, `Tatkal`) — used to *subset* picklists, never to fork the schema (see [Data Modeling](/data-model/data-modeling)).
- **Sharing:** OWD **Private** on anything with personal data, `ControlledByParent` on master-detail children, `Public Read Only` only for reference data like `PSK__c`.
- **PII rule:** never store the Aadhaar number — only `Aadhaar_Verified__c` (checkbox) and `Aadhaar_Token__c` (an opaque provider reference).
- **External IDs:** every object carries an `External_Id__c` (unique, external ID) so integration upserts are idempotent.
