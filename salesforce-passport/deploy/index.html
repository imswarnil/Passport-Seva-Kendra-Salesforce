Deploy it to your own org

Reading about a sharing rule is not the same as being locked out by one. Every lesson here describes metadata that actually exists — so put it in an org you control, log in as each persona, and try to do the things they are forbidden to do. That is where it lands.

Three ways in

Pick by how much you want to learn from the deploy itself. The CLI route teaches the most.

{% include icon.html name="rocket" size="20" %}

1 · One-click deploy

Fastest · no tooling to install

githubsfdeploy is a long-standing community tool that reads a public GitHub repo and deploys its metadata straight into an org you authorise. You log in with your own credentials on Salesforce's own login page.

{% include icon.html name="rocket" size="16" %} Deploy to Salesforce

  • {% include icon.html name="warning" size="16" %}It is a third-party tool, not run by me or by Salesforce. It asks for org access — read what you are authorising before you accept.
  • {% include icon.html name="warning" size="16" %}It deploys the whole tree, which drags in inherited template metadata and takes several minutes.
  • {% include icon.html name="check-circle" size="16" %}Best if you just want to click around the finished app.
{% include icon.html name="code" size="20" %}

2 · Salesforce CLI

Recommended · teaches the most

The way the org was actually built. You see every deploy error, which is where a lot of the real learning is — see the build log for the ones that cost hours. 

# 1 · Install the Salesforce CLI, then clone
git clone https://github.com/{{ site.repository }}.git
cd {{ site.repository | split: '/' | last }}

# 2 · Authorise your Developer Edition org
sf org login web --alias psk-dev --set-default

# 3 · Validate BEFORE you write anything (always do this first)
sf project deploy start --source-dir force-app --dry-run

# 4 · Deploy in dependency order — value sets, then objects, then the rest
sf project deploy start --metadata GlobalValueSet
sf project deploy start --source-dir force-app/main/default/objects
sf project deploy start --source-dir force-app

# 5 · Give yourself access, then look at it
sf org assign permset --name PSK_App_Access
sf org open
  • {% include icon.html name="check-circle" size="16" %}Deploy order matters. Value sets before the fields that reference them, objects before layouts, security before code.
  • {% include icon.html name="warning" size="16" %}New fields are invisible until a permission set grants them — step 5 is not optional.
{% include icon.html name="flask" size="20" %}

3 · Scratch org

Disposable · break it freely

A scratch org is a temporary org built from a config file and thrown away. The right choice for experimenting, because deleting it costs nothing. Needs a Dev Hub — any Developer Edition can be enabled as one. 

sf org login web --alias devhub --set-default-dev-hub
sf org create scratch --definition-file config/project-scratch-def.json \
                      --alias psk-scratch --set-default --duration-days 7
sf project deploy start --source-dir force-app
sf org assign permset --name PSK_App_Access
sf org open

# when you are done
sf org delete scratch --target-org psk-scratch
  • {% include icon.html name="check-circle" size="16" %}Break anything. Delete it. Make another.
  • {% include icon.html name="warning" size="16" %}Scratch orgs expire — 7 days here, 30 maximum.

Once it's deployed, do this

A deploy that you only look at teaches very little. These five take about half an hour and are where the concepts land.

{% include viz/flow.html direction="vertical" title="Half an hour that is worth more than re-reading the lessons" steps="Seed the demo data, so every stage has records in it|auto;Drive one application Draft → Delivered and watch what appears without you|user;Log in as the Front Office persona and try to open a Diplomatic application|gate;Try to grant a passport whose fee is unpaid — the validation rule should stop you|stop;Break something on purpose, then use the deploy error to work out why|user" %}

{% include icon.html name="database" size="20" %} Seed the demo data

sf apex run --file scripts/apex/seed-demo-data.apex

Idempotent — safe to run twice. It creates 24 named scenarios including the failures: an adverse police report, a rejected diplomatic grant, a QC reprint, an abandoned draft. Those are the interesting records.

{% include icon.html name="lock" size="20" %} Try what each persona cannot do

Assign yourself one persona permission set at a time and attempt the refusals in the persona list. A security model is only proven by what it stops. 

sf org assign permset --name PSK_Front_Office

Two things metadata cannot do for you

Every Salesforce org has a few settings that no deploy can express. Knowing which is part of the DevOps lesson.

{% include icon.html name="squares" size="20" %} Record page activation

Org-default and app-default page assignments deploy fine. Per-record-type activation does not. After deploying, open Lightning App Builder → Activation and assign the application record page to each record type by hand.

{% include icon.html name="warning" size="20" %} One-way Setup toggles

Enterprise Territory Management and Digital Experiences are irreversible Setup switches. This build deliberately avoids both — if a lesson mentions them, it is describing a design decision, not asking you to flip anything.
