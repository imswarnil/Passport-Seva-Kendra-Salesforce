The build log

A chronological account of how this org got built, assembled from its own commit history — which reads less like a changelog and more like a diary, because most commits explain not just what changed but what broke first. The dead ends are kept in on purpose. They are the part you actually learn from.

  1. {% include icon.html name="sparkle" size="12" %} Before anything · Phase 0

    Deciding what to build

    {% include icon.html name="clock" size="13" %} Mid-July 2026

    The goal was never "learn Salesforce features". It was to build one system real enough that the features had to show up on their own — and then explain it. A passport office turned out to be close to ideal:

    • A long lifecycle with genuine stage handoffs, so queues, sharing rules and approvals all have a real reason to exist.
    • Several distinct jobs — counter, verification, police, granting, despatch — which is what makes personas meaningful rather than decorative.
    • Sensitive personal data, which forces field-level security and PII discipline instead of leaving them as theory.
    • A process everyone has some intuition for, so the domain never gets in the way of the concept being taught.
  2. {% include icon.html name="rocket" size="12" %} Environment

    Getting an org and a command line

    {% include icon.html name="clock" size="13" %} 21 July 2026

    Everything starts with a free Developer Edition org — a full-feature Salesforce instance with small limits, which is the correct place to build something like this. Signed up, set a My Domain, and made it the working org.

    The important decision at this point is not a Salesforce one. It is choosing to work from the command line and Git rather than clicking around in Setup. Every object, field, rule and class in this build exists as XML in a repository — which is what makes it reviewable, diffable, and possible to rebuild from scratch.

    • Installed the Salesforce CLI (sf) and authorised the org as psk-dev.
    • Created an SFDX project, so metadata lives under force-app/main/default/.
    • Set the source API version and committed the empty skeleton before building anything.
    Worth knowing early Clicking in Setup and deploying from source are not two ways of doing the same thing. Anything you click still has to be retrieved into the repo, or your next deploy silently reverts it. Pick source-first and stay there.
  3. {% include icon.html name="database" size="12" %} Data model

    One object, carrying the whole lifecycle

    {% include icon.html name="clock" size="13" %} 21 July 2026

    The build starts, deliberately, with a single object: Passport_Application__c — 56 fields, six record types, one Status picklist carrying Draft all the way to Delivered.

    The instinct almost everyone has here is wrong, and it is worth naming: "Draft is one thing, Submitted is another, so they should be different objects." It sounds tidy. In practice it means copying every field between objects at each stage, re-pointing every child record, and re-teaching every report and permission set about another table. An application is not three kinds of thing — it is one thing moving through time.

    From there the model grew outward: offices, appointment slots, checklists, objections, police verification, payments, and eventually identity and fulfilment. Two objects were never in the plan and got added because the model demanded them — Citizen__c, so the applicant is a golden identity record rather than an Account, and Family_Member__c for the guardian link a minor's application needs.

    The one deliberate duplication The application stores its own name, date of birth and address even though it also has a citizen lookup. That is on purpose: a passport application is a legal instrument, and if those were live formulas, a citizen fixing a typo years later would silently rewrite what an already-granted application says was declared. Snapshot a declaration, derive a fact.
  4. {% include icon.html name="squares" size="12" %} UI

    An app you can actually open

    {% include icon.html name="clock" size="13" %} 22 July 2026

    A data model you can only see in Object Manager is hard to stay motivated by. This step built the console app, a home dashboard backed by real Apex rather than a static page, and the first demo data — so there was something to click.

  5. {% include icon.html name="stack" size="12" %} Data model · vocabulary · config

    Identity, the end of the lifecycle, and config as data

    {% include icon.html name="clock" size="13" %} 30 July 2026

    • Global value sets. Thirteen of them, so "Maharashtra" is spelled the same way on every object that mentions a state.
    • The identity domain. Citizen__c as the golden record — who a person is now, as opposed to what they declared then.
    • Closing the lifecycle. Passport__c, Print_Job__c and Dispatch__c, so a granted application actually produces a booklet that gets posted.
    • Custom metadata types. Fee_Matrix__mdt and SLA_Config__mdt — fee tables and SLA targets as deployable records, so changing a fee is a config deploy, not a code change.
    • Record types, 56 validation rules, and the sharing model. The org stops being a set of tables and starts having opinions.

    Then every layout got rebuilt and 45 quick actions wired up — which is where the platform pushed back for the first time.

    Two non-obvious platform quirks force:relatedListSingleContainer rejects a relatedListId at this org's API version, so those fall back to relatedListContainer. And FlexiPage component identifiers must be unique per page, not per region — which looks like a harmless duplicate ID until the deploy refuses it.
  6. {% include icon.html name="code" size="12" %} Apex · the incident report

    The automation layer, and everything it broke

    {% include icon.html name="clock" size="13" %} 3 August 2026

    Four triggers and a dozen service classes. The commit that deployed them took the test suite from 59% to 89% passing, and getting there surfaced problems that had nothing to do with business logic and everything to do with how Salesforce actually deploys and enforces things.

    Finding 1 · Silent skips 35 classes had no .cls-meta.xml, so the CLI silently skipped them and only their dependents failed. The cascading "variable does not exist" errors never once named the real cause.
    Finding 2 · Reserved words number, limit and like are reserved identifiers in Apex.
    Finding 3 · Invisible fields Field permissions had been generated before the External_Id__c fields existed, so those fields were invisible and USER_MODE DML failed with "fields being inaccessible". A field can exist, compile and deploy cleanly, and Apex will still refuse to touch it. The fix is not a code change at all — it is regenerating field-level security.

    A second pass took the suite to 188/188 green, and fixed six more real product bugs found by fixing tests properly rather than loosening assertions until they passed:

    • Every AuraHandledException reached the user as the literal string "Script-thrown exception", because getMessage() returns exactly that unless setMessage() is also called. All 40+ throws now go through one helper.
    • cleanUp() guarded a mass delete with != on a String — which is case-insensitive in Apex, so the guard let the wrong value through.
    • Test factory external IDs collided, because Apex test methods run in parallel and the counter restarted per method.

    That last one became the centrepiece of the testing lesson — a textbook flaky test that only appears when Salesforce happens to schedule two methods into overlapping transactions.

  7. {% include icon.html name="lightning" size="12" %} Automation

    Making the org run itself

    {% include icon.html name="clock" size="13" %} 15 August 2026

    The difference between "an object with fields" and "a system": ownership routes to the right queue the instant the status changes, the document checklist generates itself on submit, and sensitive grants are gated behind a real approval process.

    The approval that didn't approve properly The first version routed to a hardcoded admin user. Role-based approver assignment turns out to be invalid in ApprovalStep metadata — NextOwnerType has no role value — so approvals now route to an RPO_Approvals queue whose members are the Regional Passport Officer role and subordinates. Which is a better design anyway: a named approver is a single point of failure.
  8. {% include icon.html name="shield-check" size="12" %} Closing gaps

    Region sharing, reports, and a persona audit

    {% include icon.html name="clock" size="13" %} 15 August 2026

    • Region-based sharing. Criteria-based sharing can read neither a formula nor a lookup traversal, so the fix was not a smarter rule — it was a real Region__c text field, populated by trigger from the office. A field that duplicates data on purpose, because the platform made the obvious approach impossible.
    • The first reports. Zero reports existed before this. Two custom report types, five reports and an operations dashboard.
    • A persona correctness audit. Document Verification and Police Verification had been sharing one permission set despite being distinct personas. Split. PII field-level security had also drifted across four sets, letting officers edit declared PII they were never meant to touch.
    Two reporting quirks that cost real time Custom-object report types need a __c suffix and $ field separators at the metadata layer that never appear in the source file names. And a row-limited tabular report simply cannot back a Table or Metric dashboard tile — even after adding the row limit Salesforce asks for.
  9. {% include icon.html name="book" size="12" %} This site

    Turning the build into a course

    {% include icon.html name="clock" size="13" %} 15 August 2026

    The site is meta on purpose: it teaches what building the org taught, using the actual metadata as the material rather than invented examples. It reuses the org's own navy and gold so the teaching material visibly belongs to the same project as the build it describes.

    • An accidentally-committed _site/ build directory had to be removed and .gitignore hardened against it happening again.
    • The homepage stats needed a deliberate honesty pass as the build kept growing underneath them.
  10. {% include icon.html name="target" size="12" %} In progress

    The redesign: seventeen objects down to eight

    {% include icon.html name="clock" size="13" %} 15 August 2026 · current

    The uncomfortable conclusion after all of the above: the build had optimised for coverage of the domain when it should have optimised for coverage of the concepts. Seventeen objects, ~250 fields, 62 validation rules — faithful to a real passport office, and burying every interesting Salesforce idea under administrative detail nobody exercised.

    • Ten objects cut, each folded into a survivor — payments become four fields, print jobs merge into dispatch, objections become a status on the document they object to.
    • Five apps become four, each named after a job someone actually does.
    • The Support app gets rebuilt on the standard Case object, which unlocks assignment rules, escalation and Email-to-Case for free.
    • The whole design written down first — personas, journeys, trigger catalogue, access matrix, scenarios — before a single object is touched.
    Recorded honestly The cut costs the only many-to-many junction object in the model, which is a real concept the course is supposed to teach. That is written into the design docs as an open item with a proposed remedy, rather than quietly dropped. Every design decision costs something; the difference between a considered design and an accidental one is that somebody wrote down what it cost.
