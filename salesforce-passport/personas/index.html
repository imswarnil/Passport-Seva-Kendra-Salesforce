Who this system is for

A persona here is not a marketing exercise. It decides the permission sets, the queues, the sharing rules, the apps and the page layouts — so getting it wrong makes all five wrong downstream, spread across nine places in Setup. Which is why it gets written down before the schema, not after.

{% include icon.html name="lock" size="20" %} Personas are permission sets, not profiles

A user has exactly one profile, forever. So the moment one person does two jobs — a small office where the same person works the counter and answers the phone — a profile-per-persona design needs a ninth profile that is both. Then a tenth. Every one of them a clone, and a clone stops being true the day you fix something in the original.

So: one lean base profile, every persona an additive permission set, and the double-hatted humans handled by permission set groups that compose those sets rather than copying them. A profile is a job description you can only have one of. A permission set is a hat.

Write down what each persona cannot do

Most persona documents list capabilities. The refusals are more useful, for a reason that only becomes obvious once you have debugged a security model.

{% include icon.html name="warning" size="20" %} The problem with only listing grants

A permission you granted is visible in Setup. A permission you deliberately withheld is invisible. Six months later nobody can tell the difference between "we decided against this" and "we never got round to it" — and the safe-looking move is always to grant it.

{% include icon.html name="shield-check" size="20" %} The pattern underneath

  • Whoever declares something cannot verify it
  • Whoever verifies cannot authorise
  • Whoever authorises cannot approve their own sensitive cases
  • Whoever audits cannot change anything

That is separation of duties, and it is why the list has nine entries rather than three. Each split exists because collapsing it would let one person complete a sensitive action end to end with nobody else involved.
