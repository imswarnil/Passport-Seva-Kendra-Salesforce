Why a passport office

Why this teaches you Salesforce better than a tutorial does

Most Salesforce learning is scattered — a data-modelling module here, a Flow tutorial there, none of it connected to the others. A real project forces every concept to interact with every other one, which is exactly what happens on the job. A passport application is a great vehicle for that: one long-lived record, many owners, real legal/PII constraints, and a lifecycle long enough to need almost everything the platform offers.

Data modelling

16 custom objects, master-detail vs. lookup decisions that actually matter, record types instead of object-per-stage sprawl, and a deliberate case of "declared vs. current" data duplication.

Security & sharing

Role hierarchy, 8 persona permission sets, queues, criteria-based sharing rules, and field-level security on real PII — not a toy two-profile setup.

Automation

Apex triggers and service classes, auto-assignment to queues instead of hand-built assignment rules, and a real Approval Process gating a business-critical status change.

Lightning UI

Lightning Web Components, Dynamic Forms, compact layouts, custom apps per persona, Path, and a home dashboard backed by real Apex.

Apex & testing

~18 service/controller classes, trigger handlers, a shared test data factory, and 227+ passing tests — the discipline that separates a demo from something deployable.

Integration thinking

An idempotency-ready notification log, a documented n8n roadmap, and an honest list of what's still outside the org boundary.

The design

Few objects, many fields

The whole application lifecycle lives on one object with a Status picklist and record types — not a new object per stage. It's a small decision with a big teaching payoff: you learn to model state as data, not as schema sprawl, which is the difference between a Salesforce build that scales and one that doesn't.

Automatic, not unattended

Every status change cascades its required side effects — queue routing, document checklists, passport minting — but a human still decides when to move the record forward. That's the pattern real orgs use, and it's the one this teaches.

Declared vs. current

What an applicant declared at submission is preserved even after their identity record changes later — because a passport is a legal instrument, not a live profile. A subtle, realistic data-modelling lesson most tutorials skip entirely.
